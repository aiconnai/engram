## Findings (not fixed; details in the coverage map section 5)
- **G-1 CRITICAL, data-loss hazard.** `src/storage/connection.rs::restrict_sqlite_artifact_permissions` opens and closes db, `-wal`, `-shm` after every `with_connection`. Closing any fd drops all of the process's fcntl locks on that file, including SQLite's; another process that opens and closes the DB then deletes the live WAL, and later server writes go to an unlinked file and are lost on restart. Reproduced with the real server (create, raw read, create again, SIGKILL: second row gone) and minimally without engram: `.superpowers/.../task-Q4-g1-wal-lock-repro.py` (control: WAL survives True; with `open(db-shm).close()`: False). Also means C1's raw-row "unchanged" checks in `tests/http_transport_security/workspace_auth.rs` (`row_state` read while the server runs) can pass vacuously after the first read; the in-process C1 tests are unaffected. My own proof reads SQLite only after the server exits (documented in `persisted_state`). Suggested fix (not done): chmod by path without holding/closing descriptors on the SQLite files, or only at open/startup.
- **G-2.** 161 SDK/registry divergences (Python and TypeScript agree except `memory_search.include_archived`): 26 tools the server does not have (`memory_scope_*`, `memory_federation_*`, `memory_temporal_*`, `memory_add_knowledge`, ...; `resources/list` etc. are sent as tool names), 43 unknown argument keys, 11 required args never sent (`memory_synthesis`, `memory_block_*`, `memory_reflect`, ...).
