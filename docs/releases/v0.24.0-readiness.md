## verify-tag proposal

**Recommendation: retain cryptographic verification and provision explicit trust for a
dedicated release signing key.** The SDK workflow calls `git verify-tag` in preflight
and in both publication jobs, but provisions no SSH allowed-signers file or OpenPGP
release keyring. A fresh runner therefore has no project release trust material.
There is no v0.24.0 tag to reproduce a release-tag verification failure against yet;
the missing provisioning is confirmed from the workflow, not from a failed release run.

Preferred implementation, if the owner chooses SSH signing:

1. Owner provides the public key and authorized release identity; pin its fingerprint
   and allowed-signers content in reviewed release policy. Private key stays with the
   signer and is never installed on Actions runners. Do not automatically trust local
   Git config, author emails, tag contents or whatever key GitHub returns.
2. Before each of the three existing verification calls, explicitly supply the approved
   allowed-signers file using `git -c gpg.ssh.allowedSignersFile=<approved-file>
   -c gpg.minTrustLevel=fully verify-tag <tag>`. Preserve annotated-tag, tag/SHA/HEAD,
   release, manifest, registry-availability and environment checks.
3. Pin policy to an independently approved revision or release environment, and record
   its hash with the candidate. The tag being verified cannot grant trust to a new key
   merely by including a changed trust file. Key rotation needs separate owner review.
4. Test trusted signature, unknown signer, missing trust store, unsigned annotated tag,
   lightweight tag and wrong commit. Revalidate after environment approval in each job.
   Run a protected dry-run on the final reviewed implementation before publication.

If the owner already has an OpenPGP release key, use an isolated runner keyring
containing only the explicitly approved public key and validate the signing fingerprint
at the same three points instead. This keeps the existing signing method viable.
Removing verify-tag or replacing signer authorization solely with a GitHub
`verification.verified` flag is not the recommended solution.

Git documents SSH trust and failure for unlisted keys in
[git-config](https://git-scm.com/docs/git-config#Documentation/git-config.txt-gpgsshallowedSignersFile)
and signature verification in [git-verify-tag](https://git-scm.com/docs/git-verify-tag).
These are implementation references for release signing, not imported harness policy.
No signing key, GitHub setting or workflow trust configuration was changed here.

## Local packaging

Packaging `engram-core` alone cannot resolve the unpublished `engram-types` from crates.io.
Prepare both interdependent crates together, with no registry upload:

```bash
cargo package -p engram-types -p engram-core --registry crates-io --allow-dirty --offline
```

The `--allow-dirty` flag is for this preparation worktree only; repeat from the clean,
reviewed release SHA before publication. On Cargo 1.96.0 the archives are created with `--no-verify`, but the verification
step of the command above fails internally (`no hash listed` for types in the staging
registry). The evidence report records this separately from compilation of extracted
archive sources with a temporary local dependency patch. Resolve/validate this path
before publishing; real publication requires types to become available before core. See [Cargo package documentation](https://doc.rust-lang.org/cargo/commands/cargo-package.html)
for interdependent package selection and registry assumptions.
