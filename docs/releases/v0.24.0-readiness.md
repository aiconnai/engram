No private signing key, GitHub setting or workflow environment secret was changed here.

## Local packaging

Packaging `engram-core` alone cannot resolve the unpublished `engram-types` from crates.io.
Prepare both interdependent crates together, with no registry upload:

```bash
cargo package -p engram-types -p engram-core --registry crates-io --locked --target-dir /tmp/engram-pkg-verify
```

Repeat from the clean, reviewed release SHA before publication, allowing normal registry
index access. The earlier R4 observation attributed `no hash listed` to reused staging;
execution on `85502ad8` now reproduces that error even with a fresh target in offline mode.
An independent two-crate fixture fails offline and passes online. On `85502ad8`, the full
online command above passed with archive verification enabled and `--locked`; neither
Engram source nor package manifests were patched to achieve that result. A fresh target
alone is therefore not a sufficient offline workaround. Keep staging isolated and never
substitute `--no-verify` for acceptance. Real publication still requires `engram-types`
to become available on crates.io before publishing `engram-core`. See [Cargo package documentation](https://doc.rust-lang.org/cargo/commands/cargo-package.html)
for interdependent package selection and registry assumptions. The exact upstream cause
of the offline failure remains unproven; retain both failed attempts and the minimal
reproduction rather than treating an online success as a diagnosis of Cargo internals.
